## 第二轮：浅色主题（深色全绿后新暴露的一组问题）

修完 #1–#12 之后，深色 4 页全绿，**浅色仍报 29 处对比度不足**。这不是零散写错，而是同一套做法的系统性失效：

| 页面 | 处数 | 典型 |
|---|---|---|
| 桌面 | 1 | `.avatar.guest`「访」 **2.56:1**（白字压 `#94a3b8`） |
| 插件 | 19 | `.btn.small` 3.80:1、`.badge.iframe` 3.91:1、`.badge` 3.02:1、`.badge.on` 2.75:1 |
| 设置 | 4 | `.avatar.guest` 2.56:1、三个 `.btn.small` 各 4.13:1 |
| 我的 | 5 | 两个 `.badge` 3.02:1、`.badge.on` 2.75:1、`.avatar.guest` 2.56:1 |

**根因**：徽标与选中态的底都是 `color-mix(in srgb, 某色 X%, transparent)` —— 一层低透明度色压在页面上，结果是个**浅底**。
深色主题下「浅底」= 深色，配亮字可行；浅色主题下「浅底」≈ 白，配中亮度字**对比度直接腰斩**。
所以不能怪某一条规则写错——「深底配亮字」这一整套做法在浅色下不成立。

**修法**：不压深底色（会毁掉轻量徽标的观感），而是**按主题换文字**。新增一组「墨色」令牌：

| 令牌 | 深色 | 浅色 | 浅色实测 |
|---|---|---|---|
| `--accent-ink` | `#4da3ff` | `#1d4ed8` | on `#e0e9fc` → **5.50:1** |
| `--ok-ink` | `#22c55e` | `#166534` | on `#daf0e2` → **5.96:1** |
| `--warn-ink` | `#ffd700` | `#92400e` | on `#f1e0d3` → **5.52:1** |
| `--danger-ink` | `#ff6b6b` | `#b91c1c` | — |
| `--avatar-guest-bg` | `#475569` | `#526075` | 白字 → **6.39:1** |

深色取值与原来的 `--accent-2` / `--ok` / `--warn` / `--dot-off` **完全一致，故深色零变化**。
`--ok-ink` 的浅色值试过 `#15803d`，实测只有 **4.19:1 不达标**，退回 `#166534`。

## 未发现问题的项（已验证）

- **深浅双主题**：两套令牌都在，浅色是独立的 `[data-theme='light']` 覆盖，不是从深色推算。

## 第三轮：深色可读性（用户反馈驱动，不是审计发现的）

这一轮的问题审计抓不到，因为它的判据不是「达标」而是「刺眼」——对比度合规，
但视觉上不能看。两次反馈依次是「颜色有点太深了」→「窗口背景还是亮色，我要瞎掉了」。

### 3.1 深色层级差：走了两趟弯路

判据换成**看得出的层级差**，不是「越深越像 OLED」：

| 版本 | 画布 / 面板 / 悬浮 | 结果 |
|---|---|---|
| ① 纯 OLED | `#000000` / `#0c0c0c` / `#121212` | 相邻层只差 4% 明度，卡片和画布糊成一整块 |
| ② 提亮一档 | `#12151b` / `#1a1e26` / `#232833` | 分界有了，但还不够 |
| ③ **现行** | `#0e1117` / `#1e2430` / `#282f3d`，导轨 `#090c11` | 层间 RGB 差 16/19/25 + `.12~.13` 白描边 |

第三版对比度全部复测通过：正文 `#eef2f8` 压卡片 13.84:1、压画布 16.82:1；
次要文字 `#9aa3b7` 压卡片 6.14:1、压导轨 7.74:1；强调色 `#2494ff` 压卡片 5.00:1。

### 3.2 真正的刺眼源：便签插件写死白底

`public/plugins/notes/main.js` 原来是 `let bg = ctx.config?.bg ?? '#ffffff'`。
便签是**模块型插件**（`renderMode: 'module'`，与宿主同文档、不走 iframe），
于是深色桌面正中就是一块 476×182 的纯白：

```
L=1  476x182 (86632px²)  rgb(255,255,255)  div.notes-root
L=1  476x161 (76636px²)  rgb(255,255,255)  textarea.notes-ta
```

改成跟随主题求值，用 `var(--card)` 而不是写死 hex，宿主换配色时便签自动跟着走。
**同源的第二处**：`fg` 也只在创建时算一次，切主题不重算，即使背景修好文字还会停在旧主题色上。
现在 `apply()` 每次重算，`textarea` 的内联 `color` 同步更新。
`bg`/`fg` 改为**覆盖语义**：空串 = 用默认（见下方回退记录）。

> **回退记录（用户 m05927「这个便签颜色太诡异了，你还是维持原色调吧」）**
> 试过深色下把便签压成 `var(--card)` 暗块，用户反馈「太诡异」—— 便签的本体就是一张纸，
> 压暗等于丢掉「它是什么」这个信息。所以**纸面回退到原来的白**（`bgFor() = bgOverride || '#ffffff'`）。
> 但**原调色里那个真 bug 保留修复**：原来的默认文字色是 `theme==='dark' ? '#dfe3f0' : '#23263a'`
> —— 深色主题给白纸配了浅字，白底浅字几乎看不见。纸面固定白，墨水就必须固定深
> （`fgFor() = fgOverride || '#23263a'`，实测 14.90:1）。工具条/页脚同理固定 `#5b6478`（5.93:1）
> 与 `rgba(0,0,0,.10)` 描边，不再跟随主题（否则深色次要色压白纸同样看不清）。

### 3.4 一处测量陷阱（差点再次误判）

重跑探针仍读到旧令牌，查证是 `desktop/main.cjs:86`：

```js
if (DEV && !VERIFY) { win.loadURL(DEV_URL) } else { win.loadFile(DIST_INDEX) }
```

验收脚本自己设了 `WORKBENCH_VERIFY=1`，所以**加载的是 `dist/` 而非 dev server** ——
改了源码不 build 就量，量到的是旧产物。现在探针会打印 `href` 并加 `disable-http-cache`。

## 整体表现（运行时实测）

复现：`$env:WORKBENCH_DEV='1'; electron.exe desktop\perf-main.cjs`

| 指标 | 实测 | 判读 |
|---|---|---|
| 空闲 5 秒 longtask（9 窗口 + 每秒 tick） | **0 个** | 每秒调度没有阻塞主线程 |
| 连续 6 秒 idle 累计 longtask | **0 个 / 0ms** | 同上，长期稳态 |
| 页面切换提交（点 → DOM 更新） | 插件 5ms / 设置 3.1ms / 我的 1.8ms / 桌面 18.3ms | 桌面最慢是因为要挂 9 个卡片；全部远低于 100ms |
| 主题切换提交 | **2.6ms** | 换 `data-theme` 全站重算样式 |
| 强制全站重排（`offsetHeight`） | **3.8ms** | 最坏情况的同步布局代价 |
| DOM 规模（9 窗口） | 364 节点 / 9 卡片 / 8 iframe | 每卡片 28–34 节点 |
| JS 堆 | 17.3 MB used / 4192 MB limit | 占用 0.4% |

**为什么 tick 不贵**：`scheduler` 通过 `tickRef`（`useRef`）派发，不经过 React state，
所以每秒一次的 tick **不触发任何组件重渲染**，只往 iframe 发一条 `postMessage`。
这是架构上已经做对的地方，本次审计确认并记录，未改动。

**`performance.memory` 之外的注意**：`requestAnimationFrame` 帧间隔在 `show:false` 的离屏窗口里
会被节流到约 1fps（实测 avg 1002ms、119 帧全部 >50ms）。**这是测量环境限制，不是产品数据**，
所以上表改用 longtask 与提交耗时这类不依赖合成帧的指标。

**一个曾疑似性能问题的现象已排除**：初测「9 个卡片却有 8 个 iframe」看似多余，
查证后发现默认工作台自带「时钟 / 天气 / 便签」三个可见窗口，加上脚本又开了 6 个时钟窗口，
8 = 1 时钟 + 1 天气 + 6 时钟；便签是模块型（零 iframe）。**没有多余的 iframe，也没有隐藏窗口在偷偷渲染。**

## 刻意不动

插件 manifest 的 emoji 图标（`.market-card .icon`）——那是**插件自身的内容标识**，
由插件作者声明，不属于工作台的结构图标体系；工作台的按钮/导航/状态一律矢量。
